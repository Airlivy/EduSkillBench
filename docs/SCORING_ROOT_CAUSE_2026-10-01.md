# 评分慢与失败：原因确认及本轮修复

这次已经定位到两类具体问题：模型在输出评分之前耗尽了额度；代码又对同一种额度不足反复重试。不能把它们笼统地都叫“网络超时”。

## 问题、原因、解决方法

| 问题 | 原因与证据 | 解决方法及状态 |
|---|---|---|
| 设置了思考预算，模型还是一直思考 | DeepSeek 官方 Anthropic 兼容接口文档明确说 `budget_tokens` 被忽略。我们的方舟请求也确实出现预算 1024、实际输出 4096 token 且全是思考的情况 | 不再把这个参数当作可靠的硬上限。官方文档描述的是 DeepSeek 自有接口，不能据此断言方舟内部实现；但本机日志足以证明这次请求没有被限制在 1024。低思考强度也不等于固定耗时 |
| 明明连接正常，最后却没有分数 | 两次响应都是 HTTP 200，正常收到流式事件并正常结束；结束原因是 `max_tokens`，只有 thinking 块，没有 text 块 | 明确记录为“思考耗尽输出额度”，与连接中断、数据停顿、格式错误区分。这不是解析程序丢掉了正常评分，也不能用假 0 分替代 |
| 一道题反复花时间，拖累整批 | 原代码对输出截断仍自动重试。已有样例前两次耗时约 45.7、49.7 秒，第三次才拿到评分，总共约 137 秒 | 已修复：输出额度耗尽立即停止本次自动重试；持续思考直到总时限、仍无正文时也停止。保存答案和原因，继续处理其他任务。普通网络故障仍有最多三次有限请求 |
| 重新运行批次，又把同一失败重复一遍 | 单次调用不重试还不够，批次续跑也可能再次调用 | 已修复：失败绑定题目、答案、请求配置和接口地址。同一输入配置再次运行时直接报告待评分，不再自动请求；可用 `--retry-blocked-scoring` 显式尝试一次解除阻止，每次运行每个任务只解除一次 |
| 关闭思考虽然很快，但可能判错 | 前轮快速评委实测出现漏判，结构化 JSON 只能保证输出形状，不能保证判断正确 | 快速配置继续保留为试验，不直接用于正式全量结果；不删除评分项或修改对照答案来凑通过率 |

DeepSeek 参数依据：[官方 Anthropic API 兼容说明](https://api-docs.deepseek.com/guides/anthropic_api/)。对方舟参数映射的判断仍限于本地实测，不把“参数没有按硬预算生效”扩大为“整个服务存在故障”。GLM 是否具有同样的参数映射，尚未确认。

## 验证方法与边界

用保存的真实失败响应元数据回放新评分逻辑：首次调用识别为 `thinking_exhausted_output`，不再请求第二次；同一输入再次调用被阻止；没有生成 reward 或假 0 分。回放调用总数为 1。记录见 [回放验收](data-quality/SCORING_RETRY_REPLAY_2026-10-01.json)。这是旧响应回放，不能当作新模型速度测试。

回归测试覆盖截断停止、持续思考超时停止、网络故障继续有限重试、续跑不重复请求、显式解除阻止，以及换了答案不会被旧失败错误阻止。已有正常评分、缓存恢复和协议隔离测试继续保留。

本轮没有证明模型会更快给出正确分数，修好的是已确认的无效自动重试。之前的样例第三次曾成功，因此停止自动重试也意味着部分题会暂时待评分；这项取舍是显式的，不隐藏缺失结果。单次首次请求仍可能慢，快速评委准确性仍需验收。生成和评分目前仍按任务串行执行，没有声称已经实现独立的并行评分队列。

本轮修改了执行代码，正式运行要使用新的批次标签，不能向绑定旧代码的历史批次续写。请求原文和密钥不进入这份报告。

## 本轮验收结果

69 项工程测试、27 项数据测试通过。修复后的真实单题复查完成：此前失败的物理错误答案，1 次请求约 36.1 秒得到有效评分 0.64，关键项不通过，符合预先固定的对照要求；没有重试。本次成功不能否定之前的截断，也不能证明以后不失败。首个沙箱内试验因 DNS 限制未访问到服务，不计入模型失败。实测记录见 [验收数据](data-quality/SCORING_ROOT_CAUSE_2026-10-01.json)。
