# 仓库维护规范

## 入口与目录

当前评测只推荐 `python3 -m repro`。`repro/` 内的 Python 模块是实现；`legacy/` 为兼容和历史工具，不在默认流程中使用。

任务和技能放在 `data/`、`skills/`。原始运行及日志放在 `jobs/`、`logs/`；不要把原始记录当临时文件清空。`.nodecache/` 可能仍被本机框架使用，不因仓库整理而删除或移动。

## 结果发布

`results_v2/` 是尚未重新验证完成的已有汇总，`results/` 是历史发布材料。新结果先输出到独立目录，完成检查后再明确发布，不覆盖已有证据。

正式结果应同时具有：完整清单、统一评分规则、题目双条件配对、逐项评分、原回答来源以及程序和配置身份。不完整输出只能标记为预览。

## 代码、配置与结果的版本对应

1. Git 提交标识只能代表已提交内容。工作区有改动时，不能只用 HEAD 声称代码版本已固定。
2. `python3 -m repro snapshot --out jobs/snapshots/<名称>` 会记录实际源码及任务文件哈希、Git 基点、工作区状态和已有结果哈希；`source_id` 由文件清单计算。
3. 这个快照记录的是“现在有哪些源码和结果”，不能反推已有结果是由现在的代码产生的。
4. 新实验通过 `jobs/protocols/<tag>/` 固定生成材料、代码、环境和参数。改动任一关键条件就换标签。
5. 独立补评分通过 `plan.json` 固定来源及评分程序，使用 `--resume` 核验并继续；汇总保留来源清单。
6. 本次整理没有提交论文或替用户提交全部工作区。后续提交时应把评测程序、论文修改、结果发布拆成有明确范围的版本。

快照不能代替环境复现测试。本机框架补丁、缓存安装方式和真实接口仍需单独验证。

## 临时文件与归档

论文编译产物放在 `paper/build/`。本地压缩包和未引用副本放在 `.local-artifacts/`。这些位置不纳入 Git，但保留原文件及整理清单，不进行不可逆删除。

已发布的论文 PDF 和正式图表仍可纳入版本控制，不使用全局 `*.pdf` 或 `*.png` 忽略规则来掩盖它们。
