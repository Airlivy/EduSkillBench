# 评分慢与超时：定位及修复记录

更新于 2026-10-01。本文区分实测证据与尚不能确认的原因，不把所有故障都归为模型慢。

## 已定位的原因

1. **模型思考确实占主要时间。** 原设置下，同一模型的简单评分约 5 秒，完整物理题正确答案约 64 秒，错误答案约 117 秒。完整评分只有 6 项，输入约 1,882 token；最终评分正文约 160 个字符，但收到的思考内容分别约 1.4 万和 2.5 万字符。日志只计数，不保存思考正文。检查错误答案时需要核对物理计算和多个约束，这组样本主要耗时在持续生成思考内容。
2. **本机代理链路存在实际故障。** 请求继承了本机 127.0.0.1:7897 代理。有的请求在响应头到来前就发生 TLS 断连，连简单评分也失败。两轮无密钥探测均显示：走代理约 5 秒 TLS 失败，直连约 0.16 秒收到 HTTP 响应。无密钥探测的 401 只表示没有鉴权，不是有效密钥失效。
3. **旧超时策略不能区分慢与停。** 整个请求 180 秒到点就中止，即使仍在正常输出。新增日志又实测到一次先返回思考和部分评分正文、随后连续 60 秒没有任何新数据的中断，属于流停住，不能把这段等待解释成正常思考。

以前的失败日志没有分段时间，无法事后确认每一次旧超时属于哪一类；本轮也不能看到服务端内部队列或断连机器的内部原因。

## 已落地的修复

- 方舟评分请求直连已验证的域名，绕过出故障的本机代理链路。其他服务的代理设置不变。
- 等待响应头最多 90 秒；收到响应后连续 60 秒无数据则终止；只有心跳、180 秒没有模型内容进展也终止；有持续进展时允许继续，但整次请求最多 600 秒。
- 每次请求都有独立过程日志，流有进展时约每 5 秒保存一次，成功、失败时立即保存最终快照。记录首条数据、首次思考、首次正文、最后内容时间、最长间隔、字符数、事件计数、请求编号和错误类型。
- 每次评分最多三次请求。已有答案继续保留，失败仍为待评分，不生成假 0 分。这里只延长仍有进展的请求，真正断流会更早被识别。
- 容器验证器导出过程日志，备用容器评分的总时间上限同步调整，避免外层提前截断内部重试。

## 如何读日志

| 记录 | 可以判断的情况 |
|---|---|
| `awaiting_headers` + `SSLEOFError` | 尚未收到响应头，TLS 链路中断；此时不能归因于评分项太多 |
| `receiving_thinking`，最后内容时间持续增加 | 模型持续返回思考内容；是生成较慢，不是完全没有进展 |
| `stream_idle_timeout` | 连续 60 秒没有读到新的一行数据 |
| `content_idle_timeout` | 心跳可能还在，但 180 秒没有新的思考或评分正文 |
| `total_deadline` | 达到 600 秒总上限，结合最后内容时间判断是否仍在生成 |

“响应头耗时”包含连接、TLS、服务端处理及网络传输，不能直接说成纯排队时间。首条数据时间是客户端读到首行的时间，不是抓包层面的首字节时间。非流式响应不能逐段观察思考进展。

## 参数对照

没有删减题目、参考答案或评分项。把 `budget_tokens` 从 8,000 降到 1,024 的尝试未得到可靠提速：完整正确答案仍产生较长思考，随后发生断流；另一请求出现 TLS 断连。因此不把低 budget 当成已经有效的修复，也不把这些失败计为答案得 0 分。

方舟的 [Messages API 文档](https://docs.volcengine.com/docs/ark/messages-api?lang=en) 另提供 `output_config.effort` 控制思考强度；是否在当前套餐接口上有效，需要独立实测，不能仅因请求接受该字段就宣称生效。

真实对照数据和代码校验值见同目录的 `data-quality/JUDGE_LATENCY_2026-10-01.json`。这些是少量请求的诊断记录，不是全库性能统计或全库评分校准。

## 修复后真实验证

同一个 `glm-5.3-flash`，完整题面、参考答案和评分项保持相同；每个样本只发一次请求，不用重试结果掩盖失败。

| 直连配置 | 简单评分 | 完整正确答案 | 完整错误答案 |
|---|---|---|---|
| 原评分参数 | 2.44 秒，有效评分 | 35.14 秒，有效评分，关键项通过 | 170.60 秒收到完整响应，但 JSON 格式不合格，没有有效分数 |
| 另加 `output_config.effort=low` | 2.30 秒，有效评分 | 32.22 秒，有效评分，关键项通过 | 314.88 秒后耗尽 16,000 输出 token，无评分正文，没有有效分数 |

六条直连请求均收到完整响应，未出现本轮代理探测中的 TLS 断连。其中四条评分有效，两条分别因格式和输出额度失败。不能把“连接成功”写成“评分全部成功”。低 effort 这次没有带来可靠改善，因此没有改成正式默认参数；也不能从单次对照确定当前套餐接口如何映射了这一字段。

低 effort 的最后一条请求持续输出超过三分钟，新机制没有在 180 秒时无条件中止它；最终准确记录为输出额度耗尽。此前的低 budget 对照中，一条请求在已有部分评分正文后停止返回数据，新机制在连续 60 秒无数据时结束请求，并保存停顿前进展。这分别验证了持续生成和真正断流的不同处理。

本轮 58 项工程测试、27 项数据测试通过；全题库离线生成和检查通过。后续仍需处理模型偶发长思考、非 JSON 输出等评分质量问题，本次不声称模型和外部服务从此永不失败。旧目录不覆盖；代码改动后继续运行应使用新批次标签，例如 `ready-main-20261001`。

后续“关闭思考、降低预算、拆分评分项”的实测与采用决定见 [评分稳定性试验](SCORING_STABILITY_2026-10-01.md)。这些快速配置仍未通过稳定性与准确性检查；正式默认配置未替换。最新离线检查为 66 项工程测试和 27 项数据测试通过。

最新补充：输出截断和持续思考超时已停止同配置自动重试；同输入续跑不会重复请求，可显式解除。此前“最多三次”现在仅表示可重试故障的上限。详见 [原因确认与修复](SCORING_ROOT_CAUSE_2026-10-01.md)。
