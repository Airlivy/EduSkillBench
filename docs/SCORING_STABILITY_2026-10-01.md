# 评分稳定性试验与当前建议

更新：2026-10-01。结论：可以优化，但目前不能靠“少思考”或“少评几项”保证稳定。下列方案已经实测，尚没有一个同时通过速度与判分正确性的检查，因此正式默认评分配置没有替换。

## 实际试了什么

| 方案 | 实测结果 | 是否采用 |
|---|---|---|
| 将 6 个评分项拆成每次 2 个，保留完整题目和回答 | 第一组约 58 秒，第二组达到 120 秒时限，仍在思考 | 不采用；拆分也会重复发送上下文 |
| 换固定评委，关闭思考，只返回结构化判断 | 两个候选评委都约 2 秒返回，但都漏判了回答中的 `11×4=45` | 不采用为正式默认配置 |
| 关闭思考，并用程序提供算术核对证据 | 首轮 9/9 对照符合预期；扩大检查后完成 11/33，第 11 个出现内容项与关键错误项判定不一致 | 初测通过不代表全库可用，未通过扩大检查 |
| 要求每项附简短的错误原文证据 | 完成 6/33，出现无效证据触发重试，且第 6 个判分不符合预期 | 不采用 |
| 保留思考，设置低强度、1024 思考预算、4096 输出上限 | 完成 7/33，已完成样例判分符合预期；但一题前两次均用完 4096 token，只有思考、没有评分，第三次才成功，共约 137 秒 | 稳定性未通过，主动停止；第 8 个被中断，其余 25 个未开始 |

这里的“符合预期”指预先固定的对照样例要求，不是专家认证。试验没有改动测试集、评分权重或样例预期来凑通过率。不同配置不能视为严格控制所有变量的速度对照，也不能混合为同一评分协议的实验结果。

## 为什么调低思考预算还会慢

请求日志确认已经发送了低思考参数，但这条模型接口在本次试验中没有表现出严格遵守 1024 思考预算的行为：两次响应都只包含思考块，输出达到 4096 token 后以 `max_tokens` 结束。它们不是网络没连上，也不是解析程序把正常分数丢了，而是模型没有输出分数。

因此，直接缩小总输出上限可能造成“想了一半就被截断”，再触发重试，整体反而更慢。不能只看参数名，就认定模型会按指定预算交卷。

## 现在怎么运行更稳妥

1. **减小批次，保留评分要求。** 先单模型、少量题检查，再扩大；当前运行器每个 worker 的任务并发已经是 1。这样能限制失败波及范围、方便定位问题，但不保证某一题更快。
2. **保留已有答案，失败只补评分。** 当前流程已经支持；评分失败不记成真实 0 分，不为了补评分重做有效答案。原标签续跑必须保持题目、代码和协议一致。
3. **减少无关输入和输出。** 内部思考事件已经从评分输入排除；仍保留答案、工具结果、题目和完整评分依据。正式评分本来就只要求各项 JSON 判断，不需要长篇解释。暂不继续砍掉可能影响判断的证据。
4. **快速评委先过对照验收。** 固定评委、结构化输出和算术证据功能已接通，但新配置仍只适合试验。算术程序只能核对有限的数字等式，不能判断所有知识错误，也不能把“引用学生错误并纠正”直接扣分。

正式运行继续使用默认 `self-v1`，这保留了原协议，并不表示原协议没有超时。`fixed-pro-v1/v2/v3` 已明确标为实验配置，不建议拿来直接跑全量正式结果。

## 已完成的工程验证

- 66 项工程测试、27 项数据测试通过，数据发布编译检查通过。
- 单题真实端到端试跑通过：GLM 生成回答，固定 DeepSeek 评委按 `fixed-pro-v1` 评分，1/1 有效结果。这证明独立评委的接线和结果保存可用，不证明该评委准确可靠。
- 新配置单独绑定评分协议和输入摘要，不能把旧分数冒充成新配置的结果；默认协议没有悄悄改变。

完整计数、失败元数据与代码校验值见 [试验记录](data-quality/SCORING_STABILITY_2026-10-01.json)。目前没有完成全库评分校准，也没有实现“永不评分失败”。下一步应先解决扩大对照中的漏判，再决定是否推广快速评委；不继续盲目降低 token 或重跑整批。

最新补充：输出截断和持续思考超时已停止同配置自动重试；同输入续跑不会重复请求，可显式解除。此前“最多三次”现在仅表示可重试故障的上限。详见 [原因确认与修复](SCORING_ROOT_CAUSE_2026-10-01.md)。
