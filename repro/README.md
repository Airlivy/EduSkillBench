# repro/ —— v2 评测协议的可复现工具包

本目录是**修正后的评测协议（v2）**所需的全部脚本，目标是让任何人按同一协议重跑、
并自己重算排行榜。

> **先读这一句**：仓库里同时存在 **v1**（论文已发表数字所用的协议）与 **v2**（本目录）。
> 想核对论文里的数字 → 看 v1；想用修正后的、可复现的协议 → 用 v2。两者结果**不同**，
> 原因见下表。**v1 的产物刻意保留**，因为删掉它们会让论文里的数字永久无法核对。

---

## 1. v1 与 v2 的差异（都会影响分数）

| 项 | v1（已发表） | v2（本目录） |
|---|---|---|
| 模型后端 | qwen 走自有端点、flash 走 deepseek 端点、其余 ark | **5 个模型全部走同一后端（ark）** |
| 每题时间预算 | flash **300 秒**，其余 600 秒 | **统一 600 秒** |
| 评委重试 | 无（一次连接抖动即丢一格） | `max_retries=5` |
| 评委读到的轨迹 | 只保留**前 50,000 字符** | **头 120,000 + 尾 80,000**（保住写在文件里的交付物） |
| 技能注入 | 技能挂在容器目录，由 agent **自行发现并加载** | **强制把 SKILL.md 写进题面**（`_patch_force_skill.sh`） |
| 取数规则 | 每个模型各不相同（有的取最大值、有的取最新） | **统一**：干净运行优先，其次最新 |
| 缺失格 | 静默跳过；**qwen 列另有 7 个手工填入的常数** | **不填任何数**；缺失如实写进覆盖列 |
| 排行榜输出 | 无覆盖率信息 | 含 `cells` 列（如 82/84） |

**结论：v1 的数字无法从仓库复现**（含手工常数，且依赖当时的端点与超时组合）。
v2 的设计目标就是消除这些不可复现因素。

## 2. 三个必须知道的坑

1. **交付物可能写在文件里，不在最终回复里**。带技能运行时，agent 会把成果用
   `write` 工具写成文件，最终对话只剩摘要。**评估必须读工具调用内容**；只读最后一条
   对话会把这类运行判成"几乎没产出"（`lesson-builder` 尤其明显）。
2. **时间预算与条件相关**。带技能时 agent 要做更多事，超时率约为无提示组的 **2 倍**
   （实测 8.9% vs 4.6%）。预算过紧会**系统性低估技能增益**；极端例子：`lesson-builder`
   带技能需 15–35 次工具调用，600 秒甚至 1200 秒都不够。
3. **技能是否真的进了上下文，要独立验证**。框架自带的 `n_skill_invocations` 计数器
   对 opencode **恒为 0**，不能用来判断；正确做法是直接读题面或轨迹（见第 5 节）。

## 3. 三个框架补丁（跑之前必须打）

框架（BenchFlow）装在用户目录下，**升级会覆盖这些补丁，每次升级后要重打**：

```bash
bash repro/_patch_judge_retry.sh apply        # 评委连接错误自动重试 5 次
bash repro/_patch_judge_truncation.sh apply   # 评委改为"头+尾保留"，不再截掉交付物
bash repro/_patch_force_skill.sh apply        # with-skill 时把 SKILL.md 强制写进题面
```

各自都支持 `restore` 还原。

## 4. 跑一遍

```bash
# 0) 凭证：密钥放在 jobs/_resume_qwen.sh（该文件被 .gitignore 忽略，不会进仓库），
#    _env_ark.sh 会从那里读取。
#    另需本地包缓存服务（容器装 opencode 用）：_guard.sh 与各脚本会自动拉起。

# 1) 环境自检（单题，2 次运行）
bash repro/_verify_judge.sh <模型名>

# 2) 小批冒烟（1 技能 × 3 题 × 2 条件 = 6 次运行）
bash repro/_smoke_force_skill.sh

# 3) 正式跑批
bash repro/_run_batch.sh "glm-5.3 glm-5.3-flash deepseek-v4-pro deepseek-v4-flash kimi-k2.7-code"

# 4) 补缺（超时/评委失败的格，只补缺的格，不重跑整个技能）
bash repro/_retry_failed.sh <模型> 2 v2
bash repro/_autofix.sh          # 或挂这个守护，自动补到满格

# 5) 出榜（不满格会报错并列出缺格，不允许带窟窿出榜）
python repro/_validity_check.py --all --root v2
python repro/_finalize_v2.py --root v2
```

`_guard.sh` 为所有跑批脚本提供：**单实例锁**（禁止并发跑批——并发会把机器压垮，
2026-09 实际发生过：内存耗尽、WSL 拒绝服务）、每 2 分钟清理泄漏的 litellm 代理、
容器数上限、内存底线。

## 5. 怎么验证技能确实被注入

```bash
# 生成任务但不跑模型，直接看两条件的题面差异
python repro/verify_skill_injection.py
```

判据：**带技能题面比基线长 1–3 万字符、包含 SKILL.md 正文；基线题面不含任何技能内容**；
且两者差异应当只有"追加的技能块"（带技能题面**缺少**的行数必须为 0，否则基线被改动）。

## 6. 已知限制（写论文时应当披露）

- **超时与条件相关**（见坑 2）：两条件完成率不同，均值是在不同题目子集上算的。
- 部分重任务（如 `lesson-builder` 带技能）**在任何合理预算下都可能超时**，这类格应作为
  "预算内未完成"如实报告，**不要填数**。
- LLM 服务端模型会更新，跨时间重跑不保证逐位一致，应记录**跑批时间窗口**。
- 所有数值都是**单次运行点估计**，必须同时报告覆盖率；条件允许时建议每格重复 2–3 次。
